# Keystroke Biometrics: ML Team Guide

## Purpose and scope

This guide describes how to prepare the InsiEDR keystroke timing export and how to interpret the generated training and verification artifacts. The collector records timing pairs in this order:

```text
[dwell_time_ms, flight_time_ms]
```

`dwell_time_ms` is the duration a key is held. `flight_time_ms` is the interval from a preceding key release to the current key press. The sequence data contains timing values, not key codes or typed text. Timing biometrics are still sensitive personal data; use approved, access-controlled data and retention practices.

## Prepare a dataset

Run from the `InsiEDR_Server` repository root. The script defaults to a sample input and output path on the development machine, so pass explicit paths for team or production data:

```powershell
.venv\Scripts\python.exe scripts\prepare_keystroke_ml_dataset.py `
  --input "D:\data\keystroke_export.csv" `
  --output-dir "D:\data\keystroke_ml_ready" `
  --protocol auto `
  --seq-len 20 `
  --step 10
```

The CSV can contain `keystroke_timings` as a JSON array or a Python-list export, or flattened columns such as `keystroke_timings_0` through `keystroke_timings_19`. Timing pairs are filtered to dwell values from 1–1000 ms and flight values from 0–5000 ms. The collector’s normal ranges are narrower; these parser ranges also accommodate historical exports.

Identity resolution uses `username@hostname` when a usable, non-system username exists, then `agent_id`, then `hostname`, and finally `UNKNOWN_DEVICE`. When username data is absent, `agent_id` represents a workstation, not a verified human identity. Treat model results from that fallback as device-level results.

The script groups rows by resolved identity, sorts each group by timestamp, removes repeated snapshots, and stitches suffix/prefix overlap between snapshots. It does not explicitly split a person’s stream at logon-session boundaries or long idle gaps. Inspect sessionization before interpreting results as independent sessions or longitudinal behavior.

## Generated artifacts

| File | Contents |
|---|---|
| `keystroke_behavioral_metrics.csv` | Tabular collector metrics, where available. This is separate from the sequence arrays. |
| `keystroke_sequences_seq{seq_len}.npz` | Sliding-window arrays for identity classification. |
| `keystroke_verification_protocol.npz` | Enrollment, genuine probe, and impostor probe arrays for verification evaluation. |
| `agent_identity_mapping.json` | Protocol name and the separate label maps for the training and benchmark arrays. |

Load the NPZ files as follows. The identity arrays use NumPy object dtype, so only load files generated by a trusted preprocessing run.

```python
import numpy as np

sequences = np.load("keystroke_sequences_seq20.npz", allow_pickle=True)
benchmark = np.load("keystroke_verification_protocol.npz", allow_pickle=True)
```

### Sequence dataset fields

`X_train`, `X_val`, and `X_test` have shape `(windows, seq_len, 2)` and dtype `float32`. Their corresponding `y_*` fields are integer labels, and `identities_*` contains the identity string for each window. In the current implementation, window starts are separated by `step` events; windows within a split can overlap when `step < seq_len`.

### Verification benchmark fields

| Field | Meaning |
|---|---|
| `X_enroll` | Enrollment windows used to form a user template or profile. |
| `y_enroll`, `identities_enroll` | Enrollment label and identity for each window. |
| `X_probe_genuine` | Later windows from the same identities as enrollment. |
| `y_probe_genuine`, `identities_probe_genuine` | Genuine claimant label and identity for each probe. |
| `X_probe_impostor` | Windows sampled from a different benchmark identity and presented against a target identity. |
| `target_y_impostor` | The claimed/target identity label for each impostor attempt. It is **not** the source identity of that window. |
| `identities_benchmark` | Identities that produced usable enrollment and genuine-probe windows. |

The current artifact does not record the source identity for each impostor window. Use `target_y_impostor` to select the claimed user’s enrollment template; do not interpret it as the impostor’s true identity.

## Identity maps and labels

`agent_identity_mapping.json` has this shape:

```json
{
  "protocol": "open-set",
  "train": {"device-or-user-id": 0},
  "benchmark": {"held-out-id": 0}
}
```

The `train` map applies to `y_train`, `y_val`, and `y_test`. The `benchmark` map applies to `y_enroll`, `y_probe_genuine`, and `target_y_impostor`. These are distinct label spaces by design: held-out verification identities are not classifier-training classes. Do not use a single flattened map to decode both groups. Benchmark integer labels can have gaps if an identity was excluded for insufficient events; map labels by their stored integer values, not by assuming labels are contiguous.

This guide describes the current mapping format. Older generated artifacts may contain a flat identity map; regenerate them with the current script before pairing them with these instructions.

## Evaluation protocols

### `auto` (default)

With at least four retained identities, `auto` selects `open-set`; with fewer, it selects `temporal`. The retained identity count is after parsing and the minimum stream-length filter.

### `open-set`

The script deterministically shuffles identity names with seed 42, holds out at least two identities for the verification benchmark, and leaves at least two in the training/validation pool. The identity pools are disjoint. The training pool is then divided by identity into `X_train`, `X_val`, and `X_test` (approximately 70/15/15). **`X_test` is not the held-out verification benchmark**; use `keystroke_verification_protocol.npz` for open-set verification results.

For small training pools, the current sequence builder may assign the same identities to `X_val` and `X_test` when there are too few identities to make three non-empty identity groups. Check the `identities_*` arrays before treating those splits as independent evaluations.

This protocol measures whether a verification method can enroll and recognize identities not used to train its feature model. It does not establish generalization across organizations, devices, collection conditions, or time periods unless the data split is designed to represent those shifts.

### `temporal`

For each identity, the first 50% of chronological events form the training range. The remaining events are split by the benchmark builder into enrollment (60% of that remainder) and probe (40%). This gives an approximate 50/30/20 event partition. Windows are created independently after each partition, so no event crosses a partition boundary. The sequence builder further assigns identities from the training range to its train/validation/test subsets.

For fewer than four identities, `auto` chooses this protocol. Explicit `--protocol open-set` also falls back to temporal when fewer than four identities are available.

## Recommended model workflow

1. **Audit the input.** Check timestamp ordering, identity resolution, per-identity event counts, missing timing data, and whether streams cross logon sessions or long idle periods.
2. **Use only training data to fit preprocessing.** Fit scaling, feature selection, and any learned transforms on `X_train` (or the training event range in temporal evaluation). Apply the frozen transforms to validation, test, enrollment, and probe arrays. Do not fit transforms on probe data.
3. **Choose the objective.** Use the sequence arrays for a supervised identity-classification objective. Use the verification artifact for template-based or embedding-based authentication. These are related but different evaluation tasks.
4. **Tune on validation data.** Choose model settings and any decision threshold using training/validation data. Keep the verification probe scores out of threshold selection if reporting final held-out results.
5. **Report verification metrics from scores.** Compare each genuine or impostor probe with the template for its claimed target identity. Compute FAR and FRR across thresholds and report the EER threshold and operating-point FAR/FRR. State the score direction and threshold rule.
6. **Account for dependence.** Windows overlap within enrollment and probe partitions when the stride is shorter than the sequence length. They do not overlap across the enrollment/probe boundary. Avoid treating every window as an independent confidence-interval sample; prefer user-level resampling or report per-user results.

The benchmark sampler balances impostor attempts to the number of genuine probes per eligible target by sampling from other benchmark identities. Impostor source windows can be sampled repeatedly. Report this sampling design and do not treat the resulting impostor attempts as a natural deployment prevalence estimate.

For an accept rule of `score >= threshold`, calculate:

```text
FAR = accepted impostor attempts / all impostor attempts
FRR = rejected genuine attempts / all genuine attempts
```

For each impostor window, compare it to the enrollment profile indexed by `target_y_impostor`; the window belongs to another benchmark identity. If using distances where lower is better, reverse the threshold rule consistently. Report per-identity results alongside pooled values because windows and impostor samples are not independent observations.

## Quality checks before reporting results

- Confirm that expected arrays exist and have shapes `(N, seq_len, 2)`; inspect empty splits and NaN/Inf values.
- Confirm that the training identity set is disjoint from the open-set benchmark identity set.
- Verify that identity strings decoded from each label array match the corresponding `train` or `benchmark` map.
- Confirm at least two benchmark identities have enough events to produce enrollment and probe windows; otherwise impostor probes cannot be generated.
- Record the input file/version, preprocessing arguments, protocol, random seed, retained identity counts, and output artifact hashes with each experiment.
- Run the preprocessing regression suite when changing parsing, deduplication, splitting, or label mappings:

```powershell
.venv\Scripts\python.exe -m pytest tests\test_keystroke_ml_dataset.py -v
```

## Limits on interpretation

Timing pairs omit typed characters, but they remain behavioral biometric signals. The current simulated/exported dataset and identity fallbacks do not by themselves establish real-world authentication accuracy. Validate with consented, representative data; report cohort composition and per-user variation; and do not use a single benchmark score as the sole basis for access-control decisions.
